Words you will see read once, then skip

Terms from the Scope of Work that appear throughout. Nothing here is jargon for its own sake — each one names something the product has to do.

WordWhat it means here
factOne value pulled out of a document — a name, an area, a date. Facts are what we check, cite and export.
regionThe rectangle on the scanned page that a fact came from. Lets us highlight the source.
provenanceWhere something came from: which file, which page, which spot on the page, from which office, and when. We say “source location” in this document.
machine / human-verifiedTwo states for a fact. Machine means the software read it. Human-verified means a person accepted it. Only the second counts as evidence.
adjudicationThe Scope of Work’s word for the review queue: anything the software could not decide, waiting for a person.
corpus / collectionOne set of documents, usually from one office or one register series.
held linkA link between two records that is probably right but not confirmed. Usable in the product, shown with a badge, kept out of exports.

ferfarA mutation entry — the record of a change of holder, usually after a sale, succession or court order.
shuddhipatrakA correction issued later against an earlier entry. Corrections are why records need an amendment chain.
sanadA grant or title deed issued by government. Links from a sanad are legal links, so a person must confirm them.
khatedarThe holder named in a land record.
sheraThe remarks column in a register.
survey no. / CTS no.How a plot is identified — survey number in rural areas, City Survey (CTS) number in towns.

spreadOne entry printed across two facing pages.

1 · What the finished system looks like Scope of Work 3.1 – 3.10

A scanned Waqf register or 7/12 extract arrives. We record where it came from, read it, and pull out the facts. Then the path splits. The document becomes searchable straight away. The facts only count as evidence after a person has checked them.

2 · Where each fact came from — agree this first T04 · T05 · T06

Every fact we store has to point at the exact spot on the page it came from. Three parts of the product draw that spot on screen: the checking screen, the 360 view, and the citations under an answer. None of them can be started until we agree how a spot is described.

What has to be decided, in writing, before code

Where (0,0) sits

The top-left corner is (0,0) and y grows downward, the way the scan looks. Agree it once, so the extractor, the API and the viewer cannot disagree.

What the numbers mean

Store values from 0 to 1, as a fraction of the page width and height. Not pixels. The box then stays correct at any zoom and any screen size.

Crooked scans

Store the rotation and skew per page and let the viewer apply it. Old registers were photographed crooked. Ignore skew and the highlight lands on the wrong row.

Facts from more than one place

One value can come from two pages. Store a list of regions, not a single one. Build the column as a list from day one.

How we test it

Load a crooked scan. Every fact has a region, every region sits inside its page, and clicking a fact highlights the right part of the image. Then try to save a fact with no region: it must fail.

3 · How a fact goes from machine-read to checked T23 · T51 · T55

One flow with fixed steps, enforced by the database rather than by the screen. Two of the three product rules are steps in this flow.

How we test it

Call the API directly, with no user attached, and try to mark a row verified. It must fail. Try again on a handwritten row with no confirmation. It must fail too. Both are tests, not something checked by hand.

4 · Four page layouts that break normal reading SoW 3.2 · T26 – T29

These four page layouts break normal table reading. The Scope of Work calls them the most important engineering work in the product. Each one turns a messy page into clean records. Each one also has a case where it must stop and ask a person instead of guessing.

Handler 1 — multi-page spread join T26

Handler 2 — ditto-chain expansion T27

Handler 3 — continuation-row merge T28

Handler 4 — blob-cell parse T29

How we test it — the regression corpus T31 · T32

Keep one sample document per handler, each with the correct answer written out by a person, and run them in CI. Check that the records come out exactly right. Also check the safety path: a spread with mismatched rows goes to a person, and an unknown unit never quietly becomes a number. The accuracy figures from this run are a deliverable in their own right. Note that nobody has agreed yet how accurate is accurate enough (decision D-4).

5 · The checking screen SoW 3.3 · T51 – T55

The screen an operator uses all day. It is the whole verification module, and the largest front-end job in v1.

Two lanes of work T51

One lane for clean rows accepted in batches, one lane for anything flagged. A row can move between lanes, and every move is logged.

One person per row T52

Separate queues for notes in the margin, join mismatches, low-confidence fields and handwritten areas. When someone opens an item it is hidden from everyone else, so two people never check the same row.

Keyboard first T54

An operator should never need the mouse for a clean row. Allow accepting everything above a chosen confidence in one go, and keep that number in config rather than in code.

Checking never blocks search SoW 3.5

Checking decides what counts as evidence, not what can be found. An unchecked document still appears in search, marked as unchecked.

How we test it

One operator checks fifty rows using the keyboard only. Every accept writes a log entry with the user, the row, the previous state and the confidence. A handwritten row cannot be accepted without confirming it. A second operator never sees a row someone else has open.

6 · Linking records to people and property SoW 3.4 · T10 · T56 – T59

People, properties and offices become nodes. Links between them become edges. The safety comes from tiers: the tier decides what a link is allowed to be used for.

How we test it T67

Export data from a collection that contains held links. They are left out, or clearly marked — decision D-8 says which. Enforce it in the query layer, so an export format added next year gets the rule without anyone remembering to add it.

7 · Records that change over the years SoW 3.6 · T60 – T62

A land record is not a document. It is a first entry plus every change made to it since, sometimes over fifty years. Work out the current state from those changes. Never store a current value and edit it in place.

How we test it

Add a shuddhipatrak decades after the first entry, one that changes a valuation from Rs. 1,240 to Rs. 12,40,000. Then check three things: the original view, the current view and the full history are all readable; each one cites its source page; and rebuilding from the chain gives exactly the current view. Write this test first in the records module — it is the one that catches a stored, editable current value sneaking in.

8 · Search, sources, and saying “no answer” SoW 3.5 · hard rule 1 · T70 · T71 · T73

Search already works. What v1 adds is the rule around the answer: every statement is tied to a passage, and there is no answer at all when the passages do not support one.

How we test it

Ask something the documents cannot answer — “which Waqf plots in Washim are under stay?” when no such record was scanned. The system says it cannot answer. Ask something they can: every sentence carries a citation, and each citation opens the page at the right spot. This has to work whichever model provider is configured.

9 · Proving nothing was changed later SoW 3.8 · T63 – T67

This is what lets us call the records evidence. A log table on its own is not enough. The record has to be able to show it was not changed afterwards.

Log everything T07

Log every change, plus views and downloads. Today only sign-in, search and chat are logged, so widening coverage comes first, before any chaining.

Always know who did it T08

Refuse any change that has no user attached. A chain full of empty user fields proves nothing.

Six user roles T50

Six roles: records officer, operator, department head, legal counsel, IT admin, and auditor with read-only access. Department scope is a group over projects, not another folder level.

How long we keep things T66

How long to keep each class of record, replacing today's single rule of emptying trash after 30 days. The classes and defaults are decision D-7.

10 · Export, duplicates and bulk edits SoW 3.9 · T78 – T80

Export T78

CSV, JSON, XLSX, PDF and PDF/A. Every export is logged with the user, what was exported and in which format. It reads only checked data.

Duplicate detection T79

Compare hashes first. The SHA-256 is already stored but never compared, so the same file is processed again in full today. Then add fuzzy matching for pages scanned twice. Show both to an operator to decide — never drop a file quietly.

Bulk edit T80

Show a preview before applying, log every row changed, and allow a limited undo. It cannot mark machine values as checked; that only happens on the checking screen.

11 · Two ways we install it SoW 3.10 · T90 – T93

The same product ships two ways: as a hosted service, and inside a government network with no internet. The second one is pass or fail: a single outbound call fails it.

How we test it T92 · T93

Start everything with outbound network blocked. Loading documents, checking them and searching all still work on local models. Then remove a local model and confirm the call fails instead of falling back to an API. Finally, have someone who did not build it install the whole thing from the runbook.

Where the suite stands today. Nine files, 540 lines, covering authentication, tenant isolation, document and folder services, chat and search edges. Nothing covers the ingestion pipeline, the OCR path, the chunker or the migrations, and CI has no coverage threshold, so a thin suite cannot fail. Task T98 sets the threshold at today's number and raises it as these tests land.

Two defects to fix on the way past, not later. Failed image OCR no longer sets extraction_failed, so an unreadable scan indexes with placeholder text as if it had succeeded — the software says it succeeded when it did not, which is the failure this product exists to prevent.
